# Decisions and trade-offs

| # | Decision | Alternatives considered | Why this one | What it costs us |
|---|---|---|---|---|
| 1 | **Deterministic workflow with LLM steps**, not an autonomous multi-agent loop | Agent that searches, reads and decides end to end | Batch enrichment is a fixed sequence; a workflow is cheaper, testable and auditable, and every step's output is a table | Less flexible for open-ended questions (Genie covers those) |
| 2 | **The LLM resolves identity and positioning; numbers come from data** | Ask the LLM for calories / protein | LLMs guess plausible nutrition values; a wrong number in a client report is the worst failure. Here kcal error is 0.01 kcal when matched | Products with no public match get no numbers (they go to review) |
| 3 | **Cheap evidence first**: exact barcode → embeddings + LLM only for the rest | LLM for every product | 76% resolve by barcode at zero model cost; model spend goes to the hard 24% | Two code paths |
| 4 | **Embeddings + in-memory cosine top-3** for name matching | Mosaic AI Vector Search index | Reference has ~1,100 products; a vector index adds an endpoint to run and pay for with no accuracy gain at this size | At > 100k reference products switch to Vector Search (same embeddings, Delta Sync index) |
| 5 | **Evidence-based confidence** (source × identity × judge × margin × completeness), capped at 95 | LLM self-reported confidence; run the prompt N times | Self-reported scores are not calibrated; ours is: 98-100% accuracy above 50, 48% below 30 | Weights need recalibration when sources change (the evaluation notebook does this) |
| 6 | **Judge weight depends on evidence tier** (0.3 for exact barcode, 1.0 for name match) | Same weight everywhere | First run sent 50% of exact-barcode products to review although they were 100% correct; the judge is the key safeguard only for name matches | One more parameter to explain |
| 7 | **Two different models**: gpt-5.4-mini resolves, gpt-5.4-nano judges | Same model twice; a bigger model | A different, cheaper judge catches errors the first model is blind to and costs ~10% of the resolve step | Two endpoints to monitor |
| 8 | **Segment rules in YAML owned by the business** | Definitions inside prompts | Analysts change "high protein ≥ 15 g" without touching prompts; versioning re-segments only affected products | Qualitative positioning still needs the LLM |
| 9 | **Lakeflow AUTO CDC to silver**, Auto Loader per market | Notebook MERGE per delivery | Incremental by design (only new files read), expectations give data-quality metrics for free, one row per item with history of first / last week seen | Pipeline-managed tables are governed through the pipeline |
| 10 | **Incremental enrichment**: only items never enriched under the current definitions version | Re-enrich every delivery | Week 41 enriched 38 products and week 42 55, not 500; cost and runtime scale with *new* products | A definitions change triggers a larger catch-up run |
| 11 | **Lakebase for the app**, synced from gold (TRIGGERED), decisions written to Postgres | App queries the SQL warehouse directly; app writes to Delta | The review app needs millisecond point reads and transactional writes from many analysts; Postgres does both; the job applies decisions back to governed gold | Two copies of gold (Delta is the source of truth; the sync is refreshed by the job) |
| 12 | **Row filter + column mask on review history**, not on gold | Row filter on gold | Keeps the serving path simple: gold is synced to Lakebase and read by Genie without policy functions in the way; market scoping in the app is a filter, and access is controlled by UC grants on the schema and Postgres grants | Gold itself is readable by everyone with SELECT in the schema |
| 13 | **Human decisions are final**: `human_verified` rows are never overwritten, confidence 100 | Re-score everything every run | Analysts' trust: once corrected it stays corrected; also the strongest training signal for recalibration | A wrong human correction needs a new decision to undo |
| 14 | **Synthetic deliveries built from a public database** with a golden set | Hand-made fake products | Real products give real evidence (barcodes, nutrition) and an objective ground truth to measure precision, which a pure fake set cannot | Retailer quirks are simulated (abbreviations, masked barcodes, US check digit dropped) |
| 15 | Lineage from silver to gold is **not** captured end to end | Rewrite enrichment fully in SQL | The resolution step builds prompts in Python (pandas) and MERGEs from a temp view, so UC lineage shows bronze→silver and silver→embeddings but not silver→gold | Documented here; next step: write candidates to a Delta table and resolve with `ai_query` in SQL so lineage is complete |

## What I would do next with the customer

1. **Golden set from their analysts**: 200 reviewed products per market to recalibrate the confidence weights and the 70 threshold on their data.
2. **More evidence tiers** for private label: retailer web pages via a Unity Catalog HTTP connection to a search API, and `ai_parse_document` on pack images.
3. **Productionise the trigger**: the job already has a file-arrival trigger on the landing volume (paused in the demo).
4. **Agent access**: wrap the resolve step as a UC function so Northbeam's internal assistant can request new attributes through MCP.
